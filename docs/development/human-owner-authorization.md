# S2-03C project authorization and exact-action Owner approvals

This Rust/SQLite library extends merged [PR #25](https://github.com/ygtdmr/rolvya/pull/25), main `b66e078268e726fc51a100c6c80b23d93dde14a7`. Its source tree matched expected S2-03B head `0940978ff23c79abbfee6bc7aa419b90abd7768f`. [ADR 0024](../decisions/0024-project-human-roles.md), [ADR 0029](../decisions/0029-owner-controlled-project-invitations.md), [ADR 0034](../decisions/0034-owner-action-bound-reauthentication.md) and [ADR 0035](../decisions/0035-scoped-human-incident-containment.md) govern the implementation. There is no production HTTP, mail or ownership-binding adapter.

## Authority and legacy migration

[`human_auth::sessions::owner`](../../crates/persistence-sqlite/src/controller_keys/human_auth/sessions/owner.rs) provides project memberships, scoped reads, invitations and exact-action governance. Every operation rechecks the current authenticated session and project membership. Session validity alone grants no membership. `check_project_permission` is an advisory snapshot, not a capability to cache or pass to a later mutation. A future work gateway must compose current role checks with its actual work transaction and existing admission guards. Legacy `PlanStore` APIs remain trusted controller/kernel interfaces, not human endpoints.

Existing `projects.owner_actor`, plans and ledger records are preserved. A matching legacy string, email or repository username never maps to a human Owner. `bind_existing_project` requires both a current independently authenticated human session and separately verified, explicitly scoped controller-host binding authority. Production construction supplies no such authority. The immutable binding authenticates the project, initial human, legacy actor, request and timestamp with the existing opaque controller key.

Legacy financial `Approve` is denied once human enrollment is ready, including projects still awaiting binding. Its pre-human compatibility seam remains for historical synthetic core fixtures; it cannot serve as a second human-Owner policy. `Reserve`, `Report` and `Reconcile` retain their existing trusted evidence and financial guards. Unbound human installations therefore remain blocked until a reviewed binding ceremony exists. A sole Owner's independent compromise/disable response still works: governance then fails closed pending separately protected recovery, without assigning a replacement Owner.

## Memberships and invitations

`ProjectRole` implements Owner, Editor and Viewer. Bounded roster, budget and governance-history reads require current Owner authority; scoped membership and permission checks expose no cross-project rights. Membership changes use expected versions and append-only history. SQL and Rust prevent removing/demoting the final active Owner. Changes invalidate the affected user's pending project approvals without globally revoking healthy sessions or workers.

Only current Owners may issue/revoke invitations. Normal invitations grant Editor or Viewer, never Owner. A 256-bit OS-random one-use bearer is retained only for request-scoped delivery; SQLite stores a keyed commitment. Invitations bind the project, issuer session/role/security versions, immutable recipient and verified-email binding, target membership version and the approved 24-hour lifetime. Redemption requires the intended recipient's current authenticated session and enrolled factor assurance, rechecks issuer authority, and commits membership, consumption, audit and notification together. No real delivery is claimed; the private delivery callback is unavailable by default.

Owner elevation/transfer is separate. The initiating Owner supplies fresh exact-action proof; the receiving human independently authenticates and explicitly accepts the exact proposal. Ordinary invitation acceptance is insufficient. Finalization rechecks both parties' original session deadlines, epochs and membership versions. Transfer promotes the recipient before demoting the initiator in one transaction; failure leaves the initiator unchanged. Multiple Owners are supported without unanimous approval.

## Fresh proof and atomic effects

`OwnerAction` supports exact budget increases, membership changes and Owner elevation/transfer. Its versioned, discriminated, length-framed canonical encoding binds every protected field; JSON is storage only. Pending records additionally bind actor, session/generation, account/policy/security state, project, role version and target version. Engineering limits are 32 live actions per actor/project and a 30-minute pending proposal lifetime, distinct from the approved proof window.

`prove_owner_password` verifies the current Argon2id credential again, using durable account/client throttling and hashing outside the write transaction. Email-only Owners use dedicated `prepare_owner_email`, `dispatch_owner_email` and `redeem_owner_email` operations: newly issued action-bound Magic Link or OTP, independent delivery evidence, ten-minute lifetime and five failed OTP attempts. Ordinary login proofs, previews and session refreshes never authorize governance. Issuance shares bounded email throttles; lost/unverified delivery cannot mint proof. Owners need not enroll TOTP; already-enrolled factors require a fresh code with the existing global timestep/replay guard. Recovery-assured sessions do not silently bypass factors for governance.

Proof expires exactly five minutes after fresh verification. Final effect checks the original session, exact action/confirmation, current membership/security/credential versions, actual password/factor integrity and the original proof deadline. Repeated verification request contexts are rejected before another secret comparison, so audit uniqueness cannot roll back failed-guess counters while leaking a success oracle. Final trusted transport/binding checks occur after the last checkpoint and immediately before commit.

`execute_owner_action` uses one `BEGIN IMMEDIATE` transaction. A private, opaque `VerifiedBudgetApproval` composes with the existing [financial ledger](financial-ledger.md); no public allow-all callback or actor/proof DTO grants human spending. The exact currency, previous/new total ceiling and expected financial revision are checked. Ledger application, one-use authorization/effect, audit and notification fan-out commit or roll back together. Missing/ignored mandatory writes fail closed. No attempt, reservation or dispatch is created by a ceiling approval; R06 independently admits any subsequent work. `owner_action_status` exposes a scoped historical outcome after lost acknowledgment without restoring consumed authority.

## Evidence and containment

[Migration 0010](../../crates/persistence-sqlite/migrations/0010_human_owner_authorization.sql) adds bindings, memberships/history, invitations, actions/proofs/recipient consent/effects, dedicated email challenges, governance events and notification prerequisites. Published migrations 0001–0009 are unchanged. Scoped foreign keys, immutable identity/history guards, one-way lifecycles, indexed lookups and expected-version writes protect the records. Audit rows contain references and redacted changes, never passwords, session/invitation bearers, email tokens or TOTP material.

Durable notifications target other active Owners and affected membership recipients. They are access-controlled inbox/outbox prerequisites, not assertions of delivery/read status. One current Owner can approve a valid budget increase. Scoped incidents hold affected pending actions, revoke compromised session authority and invitations, and preserve unrelated sessions and previously admitted safely bounded workers.

The [focused suite](../../crates/persistence-sqlite/src/controller_keys/human_auth/sessions/owner/tests.rs) exercises actual SQLite, current password/email/factor verification, exact deadlines, cross-project substitution, multiple/last Owners, recipient consent, concurrent consumption, busy writers, aborted/ignored writes and financial rollback. Ten actual SIGKILL/reopen cases cover before/after commits for password proof, email proof, budget approval, invitation redemption and ownership transfer. The subprocess driver is test-only, uses bounded zeroizing stdin for synthetic credentials and never puts bearers in process arguments/environment. Populated v9 upgrades retain legacy accounting/users/sessions without implicit human binding; an injected v10 migration failure rolls back before successful repair. Matching-key snapshot restoration preserves a real Owner email proof; mismatched keys fail without reset. DB, available WAL and snapshot substring checks detect recognizable synthetic credential leaks, not every possible memory/storage trace.

Two independent read-only reviewers inspected actual source and the correction evidence. Reproduced regressions corrected a repeated-request guessing oracle, stale final binding/request authority and post-proof credential corruption. Mandatory-write fault tests also caught ignored membership/notification writes. These technical reviews are not human Owner approval. Exact commands, current counts and final-head CI/CodeQL are recorded in the PR; historical counts in earlier guides are not current evidence.

## Remaining production gates and handoff

Production enrollment, local ownership binding, HTTPS/browser/request verification, email/delivery attestation and incident evaluation remain default-deny. There is no admin impersonation, arbitrary account recovery, automatic rebinding, factor-removal shortcut, provider credential permission or spending fallback. Signed audit checkpoints, operational retention, encrypted off-host key recovery, real browser/mail qualification and deployment remain separate gates. Host compromise is not prevented by at-rest encryption; fresh single-factor reauthentication is not phishing-resistant MFA.

No real credentials, email, provider calls, paid work, infrastructure, issues, merges or protection changes are used. **Next dependency-ready milestone: S2-04**, verified worker bootstrap, attempt-scoped credentials, token revocation and authenticated worker authority, after manual Owner review/merge. Do not expose these library seams through unverified HTTP or synthetic authority adapters.
