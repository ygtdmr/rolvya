## Implemented boundary

`controller_keys::worker_auth::aws_fargate::execution` provides `FargateExecution`, the existing R08 `LaunchAdapter` implementation and its provider-neutral `ExecutionAdapter` stop/cleanup complement. `LaunchRequest`, `BootstrapAllocation`, `ExposureEnvelope`, `ExecutionStatus` and `TaskBootstrapLoader` are nonsecret contracts. No public success authority, production activation switch, ambient AWS profile or raw credential getter exists.

Preparation rechecks the R08 command, frozen executable leaf, R06 admission/fence, current S2-05 account eligibility, registered AWS workload and exact four-category reservation. An immutable MAC-authenticated request precedes any SDK call. A separate short launch deadline never extends the live 90-second lease; the bounded execution horizon permits independently authorized heartbeat and credential renewal. Original timestamps survive preparation replay.

Migration **0015** adds immutable launch requests, append-only execution/SDK receipts, boot/reconciliation evidence and scoped lifecycle credential-use audit. Scoped foreign keys and unique task-role/secret allocations compose with 0014's protected bootstrap. Migrations 0001–0014 remain unchanged. These tables contain no additional financial journal or worker fencing counter.

The official SDK constructs count-one FARGATE requests with exact cluster, revision, client token, startedBy, platform and private-network selection. There are **no task/container overrides**: inspected task-definition roles, digest-pinned image, command, nonroot user, resources and isolation must match the registered workload. A new immutable workload requires its own reviewed configuration. `DescribeTaskDefinition` and all network operations run outside writer transactions; current authority is checked again before `RunTask` and after its response. SDK retries are restricted to one attempt.

A committed submitting marker never causes an automatic repeat of `RunTask`. A successful receipt requires exactly one correlated task and no failures; bounded returned task/failure references are retained even for mixed responses. A task ARN proves neither Running state nor worker identity. The authenticated receipt can enter the existing S2-06B registration path, followed by C's independently checked delivery, genuine TLS exporter possession and the sole S2-04 issuer. No second credential issuer exists.

Unknown responses, missing eventually consistent tasks, expired authorization, changed authority and contradictory observations preserve uncertainty and financial holds. `ListTasks` uses explicit cluster and startedBy only, bounded pagination, and treats an empty response as inconclusive. A second dispatcher observing an unresolved submitting operation may conservatively close the financial gate and prevent the first launch. This intentional liveness limitation is tested with a deterministic barrier; the guarantee is **at most one synthetic effect**, not guaranteed launch progress. Reconciliation is required; there is no speculative retry.

Stop reasons alone confer no authority: an actual controller stop, fence, expiry, terminal or runtime boundary must exist. A durable stop intent precedes `StopTask`. A lost response or interrupted intent permits at most three explicit exact-task attempts, each retry following fresh provider inspection. Concurrent revision checks reject stale stop work. Stop acknowledgement is not termination; STOPPED is not final billing. Cleanup remains an attributable, idempotent intent against the original resource, with no artifact deletion or claim of completed AWS deletion.

The synthetic provider test runs in a child with an isolated environment.

Missing enforceability prevents production activation.
