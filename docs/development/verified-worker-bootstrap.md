# S2-04 verified worker bootstrap and scoped credentials

This Rust/SQLite library extends merged [PR #26](https://github.com/ygtdmr/rolvya/pull/26), main `fe3fb982525a1ea46f02eb93a422b9d0ed6fe3db`, whose tree matches expected S2-03C head `3a7c710ef77948523b269b7c856ecacecf60508e`. It implements the local authority and persistence boundaries of the [worker authentication policy](../architecture/worker-authentication-policy.md), [ADR 0031](../decisions/0031-atomic-task-budget-admission.md), [bounded spending](../decisions/0010-inflight-budget.md) and [provider-neutral, Fargate-first rollout](../decisions/0041-aws-fargate-first-real-worker.md). Native provider attestation and authenticated HTTPS remain unavailable; no real worker or credential delivery is operational.

## Interfaces and authority

[`controller_keys::worker_auth`](../../crates/persistence-sqlite/src/controller_keys/worker_auth.rs) provides `WorkerSecurity::open`, `prepare_bootstrap`, `claim_bootstrap`, `renew_credential`, `receive`, `revoke_worker` and request-bound delivery methods. Opening loads the existing verified controller key; it cannot initialize or replace it. Opaque zeroizing `WorkerCredential` and `BootstrapSecret` have no public export, clone or serialization. Public request objects and evidence references are data, not authorization.

Private, separately reviewed identity, transport, scheduler and incident-authority adapters default to denial. No public adapter override or development grant exists. Only private test fixtures provide scoped synthetic verification. Future AWS verification must correlate trusted AWS-side execution and launch evidence with the controller command; an ARN, environment variable, worker ID or reflected metadata is insufficient. The verifier checks installation/key identity, stage, evidence/request, provider/account/pool, immutable project/plan/task/context, admitted attempt, current fencing epoch and stable command digest. External identity verification occurs before the writer transaction; bounded synchronous current-authority rechecks occur inside it.

Preparation requires an already committed R06 admission and reconciled active R08 dispatch, an executable leaf, original financial coverage and current capabilities. Claim atomically consumes one bootstrap challenge and creates one credential generation with redacted evidence. A worker cannot create a task, reservation, attempt or effective provider launch. Tokens contain 256 OS-random bits; SQLite stores installation-keyed, domain-separated HMAC-SHA256 commitments and authenticated nonsecret records. CSPRNG errors have no fallback.

The approved clocks remain separate: **900-second maximum credential lifetime, 30-second heartbeat interval and 90-second lease**. Renewing a token neither renews its lease nor increases its spending bound. Current identity, capabilities, exact scope, original authorization deadline, enrollment state, generation, epoch, lease and finances are rechecked. Engineering bounds are a 300-second bootstrap challenge, at least 60 seconds between token generations, at most 64 generations, 8,192 authenticated request identities and 128 attributable denial events per enrollment. These are bounded library defaults, not production-qualified throughput or retention policy. Existing R08 message bounds also apply; evidence is not silently deleted.

Authenticated messages enter the existing R08 lifecycle/journal in the same `BEGIN IMMEDIATE` transaction as credential and request validation. Canonical decoded fields are checked as well as raw JSON to prevent Unicode escapes from reflecting the known bearer into persistent IDs. Replay returns the original permitted receipt only after current authority checks; changed content or revoked privileges cannot resurrect access. A result receipt remains untrusted and never marks a task successful. Narrow stop queries/acknowledgements may report existing stop instructions after a lease/financial guard fails, but cannot continue execution, renew authority or certify termination.

Legacy trusted-kernel `DurableWorkerController` callbacks reject every enrolled attempt, including retired enrollments. Unenrolled historical synthetic fixtures retain their isolated policy seam. The existing Broker worker guard also rejects enrolled control credentials: separate exact account/connection/purpose, financial and entitlement authorization is still required before any future secret operation. Worker permission variants include no human, budget, governance, Git publication or provider-secret authority.

## Revocation, persistence and failure behavior

[Migration 0011](../../crates/persistence-sqlite/migrations/0011_worker_credential_authority.sql) adds scoped enrollment, challenge, immutable credential/request, revocation and append-only redacted security records. Migrations 0001–0010 are unchanged. Foreign keys, lifecycle/version guards, uniqueness and bounded journals enforce one-use transitions. Terminal attempt transitions retire the enrollment and all generations; application guards verify that nested retirement, pending-challenge retirement and audit writes actually happened, including SQLite `RAISE(IGNORE)` failures.

Controller-authorized revocation composes existing R08 recovery and R06 fencing with credential retirement in one transaction. It preserves financial holds, accepted artifacts, independent human sessions and unrelated authorized workers. Revocation, expiry, cancellation and a stop acknowledgement do not prove provider termination or final billing. Unknown exposure blocks continuation and unsafe new admission. No replacement attempt, automatic retry, ceiling increase or financial release is introduced.

Delivery callbacks run after commit and recheck authority. **Lost bootstrap or renewal acknowledgements fail closed:** committed bearers cannot be reconstructed, and stale generations cannot retrieve a winner's token. Replayed preparation exposes metadata without its nonce. A stranded attempt needs trusted controller fencing, external/financial reconciliation and any subsequent separately approved R06 admission; no transparent recovery or blind relaunch is claimed. The current production adapters cannot perform that ceremony.

Matching-key snapshots preserve credential commitments, consumed challenges, epochs and accepted evidence; wrong or missing keys fail without resetting data. A stale snapshot may roll back revocation and cannot restore the external world. Restoration therefore retains the existing [operator pause and external reconciliation gate](resilience-fault-injection.md); fresh identity/security evidence and a reviewed activation process remain necessary. This is not completed off-host recovery or production disaster recovery.

## Executable evidence and limits

The [focused tests](../../crates/persistence-sqlite/src/controller_keys/worker_auth/tests.rs) use real migrations, protected key custody, R06 reservations, R08 durable dispatch/messages and private synthetic identity/transport grants. Integration tests preserve actual R09 independently accepted artifact bytes/hashes and a real S2-03A/B human session while revoking a separate worker. Worker bearers cannot become human sessions, memberships, Owner proofs or Broker authority.

Adversarial coverage includes forged identity, scope/capability substitution, expired/revoked/fenced authority, conflicting replay, concurrent bootstrap/renewal/revocation, delayed heartbeat/result, malformed protocol, financial uncertainty, bounded journals and known-bearer persistence. Database/WAL/snapshot scans check recognizable generated markers; they do not prove absence from all memory, storage or covert channels. Storage tests inject abort/ignored writes at enrollment, challenge, credential, lease, receipt, audit and retirement boundaries, exercise real SQLite contention and verify external identity checks hold no controller writer lock.

Ten actual SIGKILL/reopen cases cover before and after commits for preparation, bootstrap, rotation, message receipt and revocation. They assert rollback versus durable state, original permitted replay, no bearer regeneration, stable financial holds and no additional synthetic provider effects. Populated-v10 upgrade and failed-v11 rollback preserve existing human/project/financial/dispatch records without automatic worker enrollment. Exact commands/counts and final-head GitHub CI/CodeQL are recorded in the PR; independent model reviews supplement, and do not replace, manual Owner review.

The [S2-06A transport](worker-https-transport.md) implements TLS request context and response-bound credential delivery; provider bootstrap delivery remains default-deny. Production provider attestation, incident evaluation, real provider enforcement/reconciliation, gateway abuse controls, operational retention, encrypted off-host key recovery and deployment remain blocked. Existing HMAC-library internal memory copies and full controller-host compromise are outside the zeroization guarantee. No live credentials, emails, paid provider operations, infrastructure, permission changes or automatic merging are used.
