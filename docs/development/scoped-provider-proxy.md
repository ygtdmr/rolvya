## Credential and operation boundary

`HttpsWorkerServer::with_provider_proxy` constructs a closed Broker consumer. Its runtime authority remains unavailable in production. A separately established `ModelProxy` permission is required; ordinary coding/claim permissions do not imply it. Existing authenticated worker HTTPS, TLS-exporter request contexts, current credential generation, lease/fence, R08 execution, signed model-account binding, current registry grants/entitlement, exact encrypted credential version and all four financial holds are checked before use.

The worker sends only work identity, step and exact prior delivered response bytes. It cannot provide an upstream URL, headers, credentials, provider, model, account or billing mode. The controller reconstructs the existing provider-specific conversation from pinned source in memory, matches every prior response to a sealed controller-owned observation and rejects terminal continuation. This runs mediated source edits, never submitted code or OS tools on the controller.

The existing `coding_agent_calls` journal commits the canonical request commitment and original short expiry before credential consumption or network effects. A private borrowed permit binds that intent to the accepted worker/TLS context. The Broker decrypts only its exact `model-api` record and constructs an opaque API transport internally. Production `RemoteCoding` has no API-key transport field. Historical direct-adapter fixtures are compiled only in tests.

The actual OpenAI Responses and Anthropic Messages adapters retain fixed official HTTPS destinations, verified certificates/hostnames, no redirects, ambient proxy or automatic upstream retries. No generic forwarding interface or production custom-root setter exists. Responses retain only model-protocol fields, preserve opaque provider thinking/signature strings and reject recognized credential reflection, including escaped JSON tool arguments. This bounded heuristic is defense in depth, not proof against arbitrary malicious encodings, full controller compromise, memory extraction or host administrators. Sensitive temporary buffers use existing zeroizing/redacted types; HTTP/TLS implementations necessarily retain transient copies.

Proxy calls have an eight-second absolute deadline, eight rounds, 64 KiB conversations/responses, 88 KiB encoded history and eight concurrent controller proxy slots. Existing worker 15-minute credential, 30-second heartbeat and 90-second lease policies remain unchanged. The worker heartbeats before each bounded proxy call. Current authority is checked after preparation immediately before I/O and after the response before recording/forwarding success. Network I/O occurs outside writer transactions. Revocation racing an already-started upstream call cannot undo its financial exposure; response authority is withheld and the hold remains.

Duplicate/ambiguous operations never receive another execution permission. Client proxy requests do not automatically retry. Failed or missing observations prevent another turn. Usage and successful responses are not settlement, and no request releases financial holds. Original AI exposure is checked cumulatively; compute/storage/transfer holds retain their existing authority. Fixture integer terms prove local accounting behavior, not enforceable real provider charges. Unknown real charging bounds continue to deny production execution.

## Remote and CLI boundaries

An optional authenticated Fargate `credential_proxy_v1` coding profile pins the exact coding-worker command and reuses G1-04 inspection for one ephemeral `/workspace` volume, non-root user, read-only root, init process and dropped capabilities. Existing checks pin image digest, task revision, distinct roles, resources, network references and prohibit environment/secret injection or shared filesystems. Both prelaunch SDK inspection and postlaunch task inspection enforce it. Coding and independent verifier profiles cannot be substituted. Old workload JSON/MAC bytes omit the optional field.

These checks validate intended configuration. They do not establish effective IAM exclusivity, network egress, task metadata confinement, hostile-process isolation or real deployment safety. A task-role credential is accessible within its task trust boundary; neither a sidecar nor a process group protects it against malicious code there. Existing effective-IAM/network, independent-runtime, cost and real-cloud activation gates remain closed. The profile alone does not grant proxy credentials or activate a constructor.

Codex/Claude Code adapters retain pinned binaries, cleared environments, fixed argv, bounded processes and fresh account homes. The home commitment now binds installation, full task/attempt/fence, signed connection/account/credential version and adapter. Existing encrypted registry references, account-specific refresh locks and capacity/revocation authority remain authoritative; no second session store or refresh issuer is introduced. Hosted subscription/session projection and real refresh remain unavailable without separately verified provider permission and effective isolation. Harmless private CLI fixtures use no authenticated vendor session; there is no CLI-to-API fallback.
