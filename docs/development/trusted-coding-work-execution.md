## Implemented boundary

- `orchestration::coding::work::{CodingWork,SourceEntry,SourceChunk}`: strict version-1 typed packages derived from the activated task, sealed pinned source, R08 launch command, predecessor acceptances and original financial reservation. They bind installation, plan/fingerprint/context, attempt/fence, initial lease, model/effort/mode/connection/account, task instructions/scope/criteria, complete source inventory, verification policy and fixed expiry. A supplied package never becomes server authority.
- Additive `CodingWork`/`CodingSource` operations use the existing TLS worker endpoint and current S2-04 Claim permission. Every request and final commit recheck credentials, provider identity, lease/fence, R06/R08 entitlement and held exposure, plus current exact-version GitHub Owner consent. Immutable packages and bounded delivery receipts commit together. The complete bounded pinned tree is delivered in 16-KiB chunks; unsupported sizes fail explicitly, without truncation or external clone endpoints.
- `https::coding_worker::CodingWorker` reuses the authenticated client, retrieves and reconstructs source, registers/claims/accepts the existing lease, handles stop/heartbeat and submits exact locally checked `code_change_v1` bytes through the existing R08 result channel. It runs no model or OS command. Callers use its delayed heartbeat schedule during remote work; any control failure stops this session. It cannot create a task, budget, account or publication grant.
- `coding::execution::{VerifierExecution,VerifierRequest,AuthenticatedReport}`: separate execution-scoped Ed25519 authority using existing **ring 0.17.14**, not a second worker bearer issuer. Existing S2-04 enrollment is unique per attempt and remains the coding worker. Verifier grants bind their own execution/subject, workload commitment/public key, exact original work, artifact/result/policy and short validity. Ordinary worker credentials cannot create grants, fetch verifier inputs or authorize reports.
- `/v1/verifier` uses the existing rustls accept loop and request/resource limits. Each signed request includes the actual TLS exporter under a distinct fixed domain; the private client derives it from its real connection. A valid request from connection A fails on B. Receipts use stable semantic IDs independently of channel signatures. Grants, report signatures and persisted seals are checked before use. Requests recheck current authority in short writer transactions; no networking/execution occurs under SQLite write locks.
- `VerifierHttpClient` independently fetches source and raw candidate chunks, validates complete source/artifact/policy commitments, reapplies changes and reconstructs the exact candidate. `RemoteExecution` is an opaque host capability bound to the entire grant. Before filesystem effects, inputs are fully revalidated. The runner materializes a fresh owner-only tree, uses fixed absolute executable identities/argv and a cleared environment, bounds wall time and combined stdout/stderr, collects actual exit/test/output evidence, then verifies the complete resulting file inventory, modes and bytes. Extra files, symlinks, hardlinks and source mutations fail closed. No public success constructor or configurable synthetic authority exists.
- Authenticated report receipt, sealed envelope and existing `coding_verifications` commit atomically. Only G1-02's existing `accept_coding_result` can commit task acceptance. It rechecks current grant/consent/financial/fencing state and exact R08 receipt. First independent acceptance retries conservatively if its final transaction crosses a clock tick; committed acceptances retain historical verification after natural credential retirement. Reports are not acceptances. Conflicting replay/ignored writes roll back every new effect. Authenticated report-validation failures record bounded static rejection categories after rollback; final-window/storage failures remain safe denials without universal audit guarantees.
- Migration **0018** adds only work/delivery, independently bound execution/request/report evidence, revocation and restriction-only recovery holds. Existing R08 operations, R09 acceptance and Git journals remain authoritative. Published 0001–0017 and all dependency versions are unchanged.

## Offline execution evidence

The A/B/G/C integration uses real SQLite R06 admission/R08 dispatch, two separately authenticated coding-worker subprocesses, two separate verifier processes, genuine loopback rustls and existing GitHub HTTP protocol fixtures. A modifies/adds/deletes; B modifies its separate file. Fixed developer-owned Rust harnesses reconstruct and inspect candidate bytes, **compile and execute the pinned harmless Rust test fixtures**, collect actual exits/output and produce separately signed reports. No AI reasoning, real provider or hostile-code sandbox is simulated as trusted production evidence. R09 accepts both coding results, existing G aggregation gates C, and C consumes G's exact acceptance. Two independent Git refs preserve complete expected bytes, untouched files, the frozen fingerprint and approved ceiling; main remains unchanged.

Regressions cover substituted inputs/argv/paths, unexpected post-test files, expired commit-window authority, wrong keys/TLS/scope/version/artifact/policy, missing tests, failed/interrupted execution, output corruption, chronology, partial source transfer, replay/conflict, revoked consent, SQLite contention/ignored writes and concurrent A/B operations. Concurrency repetitions are not new test identities. Four actual SIGKILL boundaries cover work delivery and authenticated-report commits before/after commit; reopening verifies exact durable state, accepted sibling evidence and original holds. A committed report can feed R09 after restart without another verifier grant. Existing G1-02/G1-01 recovery tests remain intact. Source/secret substring scans are limited evidence, not proof of absent memory/hardware traces.

Engineering bounds: existing 256-file/1-MiB source and 64-KiB coding artifact limits; 64-KiB package, 16-KiB chunks, 96-KiB response, 128-KiB request, 1,024 delivery or verifier request receipts per attempt/execution, one verifier execution/report per attempt, existing two in-flight requests per attempt and bounded TLS connections. Frozen verification policy limits remain binding (at most eight commands, 8-KiB combined output and 300 seconds in the runner, further bounded by the original task). Executable hashing is bounded to 128 MiB. These are implementation bounds, not production throughput or controller-memory guarantees.

## Production gates and recovery limits

**`prepare_independent_verifier` and `RemoteExecution::from_verified_fargate` return unavailable.** Private offline establishment and capability constructors compile only under `cfg(test)`; persisted fixture grants are rejected by production builds. No real verifier launch, new billable operation, provider credentials or cloud expense is enabled. Offline verification must complete while the original attempt lease and reserved authority remain current; no paid verifier scheduling or automatic lease extension is implemented. Future Fargate verification requires independently established remote execution/image identity, effective filesystem/CPU/memory/network isolation, scoped credential delivery, separately covered financial exposure using existing R08 authority, and operational reconciliation. Ordinary subprocesses and executable hashes do not establish an immutable OCI image, protect against full host compromise or close executable TOCTOU/descendant-process risks. No production-safe sandbox is claimed.

A lost report response never mints a replacement authority. Current-authority replay is idempotent; expired/retired verifier requests are denied, and committed evidence is recovered through R09. A local restriction-only restore hold blocks work/source/report authority without erasing accepted results or releasing money. **Arbitrary unseen snapshot rollback is not detected.** Production restore activation remains blocked pending trustworthy external inventory/fencing; a SQLite snapshot cannot roll remote reality back. Encrypted off-host key recovery and real GitHub App installation/permission/protection validation remain separate gates.
