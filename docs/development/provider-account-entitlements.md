# Provider account eligibility implementation

S2-05 extends the existing Rust/SQLite authority. The verified merged base is PR #27, squash `f75f20206297d562f66b9c310237d71b5f0f84af`. Migration 0012 preserves 0001–0011. This library does not enable paid providers or subscription execution.

## Implemented boundaries

- `controller_keys::provider_accounts::ProviderRegistry` loads the existing opaque controller key. Public construction supplies unavailable provider-verification and reconciliation adapters. There is no public verifier override or plaintext credential consumer.
- `HumanAuth::prepare_provider_connection` stages immutable connection/grant changes. The existing S2-03C exact-action password/email proof, voluntary enrolled-TOTP protection, current session/membership checks, one-use effect, audit and notification transaction remain mandatory. Preparation is not consent. Connection ownership is an immutable human identity; it never derives from a legacy actor or credential string.
- `HumanAuth::verify_provider_account` takes a typed `ProviderVerificationRequest`. Independent provider inspection occurs outside SQLite transactions; current authority, consent versions, credential/evidence deadlines and session authority are rechecked before commit. No production verifier exists yet. Project-scoped `provider_connections` exposes bounded redacted metadata, not a current eligibility grant.
- Signed append-only project-grant histories preserve the exact evidence referenced by prior attempts. Versioned records bind installation, provider, account, API/CLI mode, integration, project, consented models and the exact encrypted Broker credential reference. Account capability facts and project permission scopes are separate. A full capability catalogue refresh cannot expand a project's consent. Public policy citations, native CLI authentication and provider catalogue presence are insufficient account evidence.
- `RegistryPolicy` composes existing scheduler/worker policies without widening them. R06 admission checks entitlement and atomically records account capacity, four-category financial reservation, attempt, fencing, audit and outbox. Replay rechecks current authority and consumes no second slot or hold. R08 rechecks queued launch authority; denial records a redacted blocked event. Previously uncertain operations retain the existing reconciliation path.
- API and CLI modes cannot substitute for one another or select another account. CLI evidence requires specifically permitted hosted use, independent account permission, isolated-home metadata and account-specific serialized refresh. An unresolved refresh remains blocked after its nominal deadline. No host environment credential lookup or CLI-to-API fallback exists.
- Initial leases and authenticated heartbeat renewal are capped by provider/credential deadlines as well as the original execution permit. Worker token lifetime remains a separate control. Provider withdrawal still permits the existing narrow authenticated stop/acknowledgement path; it does not authorize continuation or release exposure.
- Broker checks map model account/provider/credential identity separately from worker infrastructure. S2-04 control credentials still confer no provider-secret permission. Real credential consumption and remote CLI credential delivery remain unavailable.
- Capacity release requires independently verified model-provider termination and final usage, retired execution, R08 final/no-effect observation and finalized R04 accounting. Cancellation, disconnect, lease expiry and local revocation are insufficient. Release never edits financial holds and does not reset quota usage.

The pre-installation synthetic kernel remains compatible only within its exact historical synthetic model/connection/infrastructure namespace. Once controller custody or an account is enrolled, missing registry authority fails closed. This compatibility seam is not a real-provider permission.

## Production gates and handoff

All real account enrollment, provider consent/authentication, entitlement/capability/quota inspection, cost enforcement, model calls and CLI execution remain blocked. Official pages reviewed on 2026-10-28 are [dated evidence](../reference/provider-cli-api-policy-evidence.md); they establish no Rolvya registration or account-specific authorization. Complete deterministically ordered provider capability catalogues are required to avoid conservative version invalidations from order-only changes.

Pool/provider/account capability bindings are enforced in the synthetic gate. Region, resource class and CLI-home identifiers are recorded constraints; they do not prove physical remote isolation, region or credential custody. Enabling a real adapter requires independently verified infrastructure/attestation evidence and enforcement. SQLite reservations do not guarantee third-party spending limits. Snapshot restoration does not roll external operations or invoices backward; uncertain exposure remains an operator reconciliation gate. Emergency off-host key recovery, operational SMTP/HTTPS, provider authentication and deployment are unimplemented.

Next dependency-ready work is a separately scoped review of trusted provider/account consent, verification and capability adapters against these contracts, together with authenticated transport and independently enforced remote isolation/cost bounds. No account authorization, paid rollout or next slice is started here. No new dependency, live credential, email, provider operation or cloud spending is used.
