Base: merged [PR #30](https://github.com/ygtdmr/rolvya/pull/30), main `2896bbd7b99c2c96ae6dd9a8137b73b5776b3d36`, with the complete `7eba1358b62378bd198a0d245147225e2a9a73f4` source tree. It does not authorize AWS operations or paid execution.

## Implemented trust chain

- `HumanAuth::prepare_infrastructure_account` stages an exact project/account/partition/region/cluster/workload/Broker-reference proposal. Existing authenticated Owner membership, fresh primary/factor proof, confirmation and atomic Owner-action execution establish durable consent. Consent alone neither enrolls an account nor launches work. Disconnect is an exact metadata-only Owner effect and remains possible after credential loss or expiry.
- `FargateIdentity::verify_account` uses current consent to consume the exact encrypted Broker credential through a private AWS SDK capability. Regional `GetCallerIdentity` checks the explicitly selected controller account/role/role ID. No public plaintext getter, caller-installed verifier, environment/default credential chain or global profile is introduced. Enrollment rechecks the short-lived signed controller observation at commit.
- `SecureFargateBootstrap` requires an existing R06/R08 execution, reservation, immutable scope, current S2-05 eligibility, lease/fence, approved infrastructure account and an independently verified exclusive task role/resource. Forward [migration 0014](../../crates/persistence-sqlite/migrations/0014_aws_protected_bootstrap.sql) records consent, resource binding, encrypted proof material and append-only lifecycle evidence; migrations 0001–0013 are unchanged.
- Initial protected material is the existing S2-04 OS-random 256-bit bootstrap secret. Its encrypted delivery copy is committed in the same transaction as the original one-use challenge. Purpose-specific XChaCha20-Poly1305 uses a fresh DEK and separate random data/wrapping nonces, with authenticated installation/key/execution/challenge metadata. SQLite, WAL and ordinary snapshots contain no raw bootstrap value.
- The selected distribution pattern is a separately provisioned, empty, per-attempt Secrets Manager resource with its complete returned ARN and an exclusive task role. The SDK validates metadata, validates/installs/reads back the restrictive resource policy, then publishes the protected value under a stable VersionId. Retries use the same encrypted material and version. A resource name/ARN is public metadata, not authentication. Resources are never created by this slice.
- `DeliveredPossession::authenticate` signs canonical, length-framed, domain-separated challenge/operation/request/installation/project/plan/task/attempt/epoch/generation/resource metadata with the protected secret. Both client and server obtain the binding from their actual rustls stream using `EXPORTER-Rolvya-worker-v1` and `wire-v1`. A different TLS connection cannot reuse the proof. ECS inspection is correlation, never an AWS-signed task attestation.
- Fresh AWS inspection and final authoritative SQLite rechecks precede the existing S2-04 credential effect. Its 256-bit opaque credential is the sole worker bearer. Core challenge consumption, protected-proof consumption, credential generation, audit and cleanup intent commit together. A lost response cannot retrieve that credential again.
- Renewal requires a current bearer plus a new OS-random protected secret/challenge/version bound to the previous credential and next generation. It preserves the existing 15-minute credential, 30-second heartbeat and 90-second lease rules. Current account/Broker/consent/eligibility/fencing checks protect continuation. The existing reduced stop-receipt path does not restore execution authority or release holds.

The source is in [AWS bootstrap modules](../../crates/persistence-sqlite/src/controller_keys/worker_auth/aws_fargate.rs), [scoped Broker consumption](../../crates/persistence-sqlite/src/controller_keys/secret_broker/aws_consumer.rs) and the [bound TLS client](../../crates/persistence-sqlite/src/controller_keys/worker_auth/https/bound.rs). New exact dependency: `aws-sdk-secretsmanager =1.100.0` (Apache-2.0, declared Rust 1.91 minimum); existing pinned Rust 1.99.1 and AWS/Smithy dependencies are preserved. Hyper enables its existing version's client feature. SDK retries remain disabled; bodies, timeouts, batches and generations are bounded.

## AWS guarantees and activation gates

Official sources checked **2026-10-29**:

- [Task roles](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html), [task versus execution roles](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/security-iam-roles.html), [task overrides](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_TaskOverride.html), [task metadata](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v4.html), [GetCallerIdentity](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html) and [Rust credential loading](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/credproviders.html): neither copied metadata nor a task-like role-session name proves request origin. STS/SigV4 authenticates the selected AWS API caller, not arbitrary additional Rolvya challenge fields.
- [Sensitive-data delivery](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/specifying-sensitive-data.html), [container dependencies](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDependency.html) and [SSM integration](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-ssm.html): environment injection is excluded. No sidecar or multi-container exception is added to the existing workload guard. The intended trusted bootstrap process retrieves before model execution; this does not protect against complete task compromise.
- [Secrets Manager resource policies](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_resource-policies.html), [identity policies](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_iam-policies.html), [IAM condition keys](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html) and [GetSecretValue](https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_GetSecretValue.html): access is role-based. The policy explicitly denies other `aws:PrincipalArn` values and expired reads, and allows only the exact role/resource. Reads pin the exact ARN and VersionId. Secrets Manager does not provide one-use reads or automatic TTL deletion.

**Production issuance remains hard-disabled.** Necessary independent evidence is unavailable for effective IAM policy, task-role exclusivity, PassRole/RunTask restrictions, trusted launch receipts and real remote task-role credential loading. Structural JSON checks and private synthetic observations cannot establish those properties. The SDK task-side reader is tested privately; a production credential loader is not fabricated. Shared-role tasks can read the same resource; tests demonstrate that fact and reject activation without separate exclusivity evidence. No public success-verifier override exists.

Effective IAM/network enforcement, actual task identity, enforceable cloud spending limits, real cancellation/final billing, authorized resource provisioning and isolated live validation remain future gates. A local revocation cannot prove AWS termination. Cleanup records per-challenge intent, not deletion of an entire resource still needed for renewal or verified destruction of AWS versions.

One-use protection survives tested process death against the current authoritative database. **Arbitrary rollback of the entire database can roll back consumption too.** No independent restore fence or complete emergency recovery is implemented. Matching keys and a consistent snapshot do not prove the external world was restored; production activation stays blocked until trusted restore/reconciliation evidence exists. No physical power-loss, production durability or exactly-once AWS claim is made.
