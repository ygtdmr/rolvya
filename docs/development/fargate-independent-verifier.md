## Implemented

`FargateExecution::open_verifier`, `prepare`, `launch_verifier` and `authorize_verifier` derive a separate execution from the existing received coding artifact, frozen work/source, exact policy and original admitted attempt. The verifier has distinct account scope, task-definition revision, digest-pinned image, task/execution roles and protected secret resource. A worker cannot install its own public key or verification authority. Fresh Ed25519 keys use existing ring 0.17.14 and its OS random source; private PKCS8 material has purpose/installation/key/launch-bound XChaCha20-Poly1305 custody with independent wrapped DEKs. No dependencies changed.

The existing AWS request/event/SDK-receipt journal now distinguishes `coding` and `verifier` operations. Migration **0019** copies original record text and MAC bytes unchanged, keeps global task-role/resource uniqueness and append-only evidence, and adds only the encrypted delivery copy. Published 0001–0018 remain unchanged. There is no additional scheduler, DAG node, financial ledger, worker bearer issuer, R09 acceptance table or Git publisher.

Preparation verifies current R06/R08/S2-05 authority, source/Git Owner consent, infrastructure Owner consent and Broker credential version. Checked four-category arithmetic fits **both** recorded coding exposure and verifier exposure into the existing original reservation. One admitted attempt can have only one independent verifier operation. No additional budget or free-verification assumption is created. Price/configuration envelopes are not proof of enforceable AWS cost ceilings.

The official ECS SDK constructs the existing count-one FARGATE RunTask with exact task definition, immutable request commitment, purpose-specific stable client token, private-network settings and no overrides. The submitting marker precedes SDK calls. Receipts correlate exact task/account/region/cluster; ambiguous/lost responses retain uncertainty and original holds. An explicit verifier operation cannot substitute for the coding worker's R08 LaunchAdapter or S2-04 receipt binding. Unknown submission propagates to the existing financial gate. Repeated submission never blindly repeats RunTask. Existing stop/reconciliation/cleanup compose by purpose; stop acknowledgment and STOPPED never settle billing.

Workload inspection reuses official DescribeTasks/DescribeTaskDefinition correlation. Verifier configuration additionally requires non-root, read-only root, one fixed ephemeral `/workspace` volume without host/EFS/FSx mounts, init process enabled and all Linux capabilities dropped. Exact executable hashes, argv, verification policy and task resources remain bound. Effective IAM, egress and runtime confinement are independent gates.

Protected delivery reuses exact-resource Secrets Manager policy validation/readback and stable version semantics. The production adapter consumes only the exact scoped Broker capability and never ambient credentials; its effective-distribution gate is unavailable. `VerifierTaskLoader` selects only the existing official ECS credential provider and exact secret/version. Its production constructor remains denied. `VerifierCredential` is opaque/non-clonable/non-serializable and creates the existing verifier HTTPS client without a raw-key getter.

Fresh configuration and restricted-delivery observations are authenticated in the existing AWS SDK receipt journal. The grant references its **first exact committed observation**, preserving stable delivery after lost acknowledgments or ignored final writes. Current requests use only typed authorization observations and their original absolute expiry; ordinary lifecycle inspection cannot refresh them. Explicit trusted refresh repeats inspection/delivery checks without minting another grant. Historical accepted evidence checks its original proof and remains valid after ordinary termination; current authority does not survive revocation, expiry, fencing or financial risk.

Actual TLS exporter signatures and the existing execution/report protocol remain mandatory. Reports are evidence only: existing R09 alone accepts the result, and the existing GitHub publisher alone publishes accepted bytes. The runner now kills ordinary process groups on completion, timeout, output failure or cancellation. This does not contain a hostile process that escapes its group or compromises the host.

## Not verified in AWS; production disabled

There is **no production activation switch**: mutating ECS transport, effective restricted distribution, Fargate grant validation, task-loader activation and `RemoteExecution` establishment remain hard-disabled. Persisted private fixture grants cannot become production authority after restore. Production coding validation/publication are not enabled by this milestone.

Missing evidence includes actual Owner/account setup, effective IAM/SCP/PassRole and exclusive secret access, immutable runtime/image and executable protection, hostile child-process/credential separation, metadata and `/proc` confinement, CPU/RAM/disk/network enforcement, bounded total cost and stop/reconciliation, and independent operational inventory/restore fencing. Same-task processes can access task-role credentials; task-level Fargate isolation does not establish signing-key safety against untrusted code inside that task. Ordinary process groups and subprocess tests do not establish a production sandbox. No arbitrary snapshot rollback detection or automatic restore clearance is claimed. Encrypted off-host key recovery remains separate.
