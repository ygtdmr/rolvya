## Cryptographic envelope

Pinned direct dependencies: RustCrypto `chacha20poly1305 = 0.10.1` with `alloc`, `poly1305 = 0.8.0` with `zeroize` (explicit feature unification for authentication-state wiping), and `subtle = 2.6.1` for constant-time replay-tag comparison. Transitive AEAD/cipher dependencies are checksummed in Cargo.lock. The mature 0.10 API fits existing RustCrypto dependencies; availability of 0.11 is neither a vulnerability claim nor a completed vulnerability audit. AEAD dependencies permit MIT/Apache-2.0 choices; subtle uses BSD-3-Clause. Complete release-artifact notices remain a release gate. Existing getrandom 0.3.4, zeroize 1.9.1, HMAC 0.12.1 and SHA-256 0.10.9 remain pinned.

Each immutable secret version gets an independent OS-random **256-bit DEK**, a **24-byte data nonce** and a separately drawn **24-byte wrapping nonce**. XChaCha20-Poly1305 encrypts content under the DEK and wraps the DEK under the loaded 256-bit KEK. SQLite contains only ciphertext/tag, the 48-byte authenticated wrapped DEK and nonsecret metadata. A unique `(wrapping KEK ID, version, wrapping nonce)` constraint rejects duplicate committed wrapping nonces; equal data/wrapping nonces are rejected. Entropy failure aborts without fallback. This follows randomized XChaCha nonce practice; no deterministic nonce generator or cryptographic certification is introduced.

The canonical binary AAD uses fixed domain bytes, fixed-width big-endian integers and explicit u32 byte-length-prefixed UTF-8 identities. It binds installation, project, account, connection, provider, explicit mode, record, purpose, immutable record version, envelope/cipher version and content-origin KEK ID/version/format. Wrapping AAD additionally binds a separate operation domain, wrapping KEK metadata, data nonce and SHA-256 of the **ciphertext**. Secret-content comparisons never use plaintext SHA-256.

Separate content-origin and wrapping metadata let a future reviewed wrapping revision retain the original content AAD. **Only the currently loaded key is accepted now.** There is no keyring search, fallback, KEK rotation or rewrap API. Future rotation must authorize wrapping revisions and retain any required historical receipt keys. Versioned request commitments identify their own KEK ID/version; unsupported versions fail closed.

Application-owned KEK, DEK and plaintext buffers are zeroizing; in-place AEAD buffers are wiped on failure. AEAD/ChaCha/Poly1305 wiping features are enabled. This is best-effort memory handling: HMAC 0.12.1 does not wipe all internal digest/key-pad temporaries, and zeroization cannot guarantee absence of compiler/OS copies, swap, core dumps or extraction after controller-host compromise.

## Authority and lifecycle

`SecretBroker::open(&ControllerBootstrap)` loads the verified existing S2-01 key and its bound SQLite store. It never exports raw KEK bytes or creates a replacement key. `ControllerKey` remains opaque, non-cloneable and non-serializable.

Public operations are `create_connection`, `put_secret` (create or expected-version replacement), `metadata`, `verify_integrity`, `revoke_connection` and `use_secret`. Input `SecretValue` is bounded to **0–65,536 bytes**, non-cloneable, non-serializable and Debug-redacted. `use_secret` returns only a redacted receipt. No public plaintext getter/export, arbitrary callback, consumer override or development grant exists.

All public construction installs **unimplemented, denying authorities**. Private, separate seams distinguish authenticated human/admin actions, trusted internal use, worker identity, provider/account entitlement, scheduler policy and bounded trusted consumption. Tests install unmistakably synthetic implementations inside `cfg(test)`; record IDs, actor strings, peer references and request objects are never production authentication. Metadata permission does not imply storage, replacement, revocation, integrity/use or recovery/export permission. No export/recovery operation is implemented.

`LocalIntegrityInspection` is an explicitly controller-local, no-I/O operation behind the same sealed consumption boundary. Model proxy and refresh operations require worker scope. They reuse [R06/R08 guards](../../crates/persistence-sqlite/src/worker_control/mod.rs): active dispatch/session, immutable binding/context/plan, verified peer/capabilities, distinct `UseCredential` permission, selected connection/account/provider/mode, current lease/fence, dependency evidence, execution policy and all four financial categories. Unknown exposure, revoked authority, stopped/fenced/expired attempts and insufficient hold coverage deny use. No worker is given a credential or controller key.

Short `BEGIN IMMEDIATE` transactions serialize lifecycle and scoped use decisions. The only consumer seam is private, synchronous, bounded and forbids I/O/external effects; production supplies no implementation. Future provider consumption needs a separately reviewed effect/authorization protocol and must not put network operations inside this transaction. This milestone does not assert external exactly-once use or cancellation.

Forward [migration 0007](../../crates/persistence-sqlite/migrations/0007_secret_broker.sql) adds scoped connections, logical records/current versions, immutable encrypted versions, redacted append-only events and bound request receipts. Composite foreign keys prevent cross-project audit/record links. Replacement requires the expected version, generates a new DEK/envelope and never overwrites historical content. Revocation is one-way and never silently reconnects or selects another account.

Replay uses domain-separated **HMAC-SHA256 keyed commitments**, including action, actor/request, full scope, version and plaintext only when comparing an authorized write. This is necessary for conflicting-payload detection without persisting a low-entropy plaintext hash. The tags are internal replay metadata, never general audit payloads or public lookup tokens. Use replay rechecks current authority, entitlement, revocation, version, worker scope, lease/fence and financial safety before returning the original receipt; it does not consume credentials again. Integrity checks reauthenticate stored bytes even on duplicates. Unknown-project denial preserves the original error.

Record reads preflight byte lengths before allocating envelopes. `length(CAST(... AS BLOB))` handles NUL-prefixed corrupt text correctly; connection/head queries compare identities in SQL and return only bounded labels/integers. Bounded receipt projections and fallible decoding reject malformed records without panic. This is not a general hostile-database or full-file-encryption guarantee. There is no cleanup API: encrypted lifecycle/audit/replay history remains preserved pending a separately reviewed retention/rotation policy.

## Executable verification

[Broker tests](../../crates/persistence-sqlite/src/controller_keys/secret_broker/tests.rs) use real S2-01 initialization, real AEAD and real SQLite. [Public API tests](../../crates/persistence-sqlite/tests/secret_broker.rs) and compile-fail doctests check bounded/redacted input and nonserialization.

Coverage includes all scope/version/installation/key substitutions; independent DEKs/nonces for identical plaintext; modified ciphertext/tags/wrapped keys; malformed/oversized/NUL metadata; nonce constraints; empty/max values; failed entropy at every draw; actual SQL insert/upgrade rollback; create/replace/revoke replay and conflicts; concurrent creation/replacement/revocation/use; authority revocation during encryption; default denial and missing-key restart; current admitted worker, wrong peer/attempt/project/epoch, expiry, fencing and unknown exposure. Existing financial holds/ceiling and accepted synthetic core results remain intact.

A real two-project/two-account flow encrypts distinct markers, consumes internally, rejects tenant/ciphertext substitution, closes/reopens SQLite, loads the same key, revokes one connection and preserves the other. A consistent snapshot is copied to an isolated database directory with separately matched test custody. Correct decryption and byte-identical ciphertext survive; wrong custody fails without reset. Disposable DB/WAL/snapshot scans check recognizable plaintext **and actual KEK/DEK bytes**. Substring scans do not prove absence from every memory/filesystem/hardware trace.

Actual subprocess SIGKILL/reopen runs at four points: before encryption, after encryption, before commit and after commit/before acknowledgment. Aborts leave no record/version/request or accepted-store event; committed replay returns the original receipt/envelope without new entropy or extra active versions. The separate S2-01 twelve-checkpoint suite remains unchanged. Physical power loss, live provider effects and off-host recovery are not verified by these tests.

Fresh-context read-only crypto and authority reviewers inspected actual code and independently ran focused tests. Regression tests reproduced and closed missing-worker scope, project-existence denial errors, integrity-request cross-record replay, a lost denial audit after in-flight revocation NUL-prefixed size checks and lease expiry during receipt lookup. Current authority is rechecked immediately before committing use receipts; late denial rolls back provisional accepted evidence. Review also enabled available Poly1305 wiping and repaired the migration test fixture. These reviews are scrutiny, not authenticated human approval.

Fresh local verification passes **364 unique workspace Rust tests** (including 44 broker unit tests with one subprocess driver, one public broker test and three persistence compile-fail doctests). Migration replay has eight checks, the controller suite has 203 and Python has 23. Focused/replay reruns do not inflate unique counts. Exact commands and final-head CI are recorded in the PR. Required commands remain the existing Rust fmt/Clippy/locked tests/check, `ci.py rust/inventory/repository`, Node controller tests, Python checks and migration replay. Focused commands:

This focused measurement followed the workspace gates and uses 28-byte synthetic values in 32 records under one connection; it excludes fixture/key setup. This is not an isolated crypto/startup benchmark, production capacity guarantee, SLO or formal cryptographic certification. No live calls or costs were involved. Dependency vulnerability auditing remains unverified if cargo-audit/advisory data are unavailable. Graphify is refreshed; SQL is directly inspected and executed when its parser is unavailable.
