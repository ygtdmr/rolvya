# ADR 0045 — Automatic local master-key unlock for encrypted SQLite secrets

Status: **Approved — automatic unlock and protected controller-host key file**  
Date: 2026-10-25  
Owner decision: “otomatik yeterli olacaktır”, in response to automatic loading from a protected server-side file rather than manual unlock after every restart.

## Context

[ADR 0044](0044-encrypted-sqlite-secret-storage.md) selected application-layer encrypted credential records in the authoritative SQLite database, accessed only through the trusted Rust Secret Broker. The decryption/master key must stay outside the database, ordinary database backups, source and container images. The Owner selected **automatic restart/unlock** without an administrator entering a key every time Rolvya restarts.

## Approved decision

1. **Automatic unlock on the remote Rolvya controller host:** the trusted Rust Secret Broker loads its existing master/key-encryption secret at service startup from a **separate OS-protected local key file**. No interactive password, manual unseal or cloud KMS/Secrets Manager call is required for ordinary restart. This is the **first implementation**; do not introduce a local agent on any user's personal computer.
2. The file is **outside SQLite, its journal/WAL, normal DB backup paths, web roots, repositories, app bundles, logs, container images and ordinary config snapshots**. It is managed as a deployment secret, not checked in or generated by any public build artifact.
3. **Least-privilege filesystem controls** are mandatory: use a dedicated non-root service identity; owner-only permissions (Unix file mode no broader than `0600`, parent directory no broader than `0700`, or equivalent on the target operating system); reject symlinks/unsafe ownership or overly broad permissions where feasible. Other users, web frontend and remotely executed worker identities may not read the file. Exact filesystem path, service manager and mount/provisioning mechanism remain implementation choices.
4. **First-time initialization is a distinct, explicitly authorized setup operation**, creating or securely provisioning high-entropy key material only if no existing encrypted credentials or key state exist. On subsequent startups, **if the key file is missing, invalid, unreadable, mismatched or compromised, fail closed**: do not silently create a replacement key, wipe or overwrite ciphertext, attempt a different connection/account or run paid work requiring secrets.
5. **Secret encryption remains within the trusted Rust broker before SQLite persistence.** Startup key loading is not a license to expose the key or raw provider API/CLI credentials to remote workers, environment dumps, crash logs or AI model contexts. Prefer broker-proxied API calls; use separately reviewed account-scoped isolated remote CLI grants only when permitted by the provider.
6. **Tradeoff explicitly accepted:** automatic host-local unlock prioritizes unattended service recovery and low operational overhead, but **a full compromise of the running controller host or sufficiently privileged host files can expose the key and decrypt stored secrets**. This is not hardware-backed key custody, offline sealing, encryption of the whole SQLite database, or a claim of protection after root compromise.
7. **Recovery and rotation remain essential security requirements, not an interactive startup requirement.** Never bundle the master key into an ordinary DB backup. A separately protected recovery copy/restore workflow must be designed, authorized and **tested** before production with real stored credentials; no automatic upload or mandatory paid manager is approved. Backup without a matching key may leave encrypted credentials irrecoverable. **Subsequent [ADR 0046](0046-off-host-encrypted-master-key-recovery.md) now approves an encrypted off-host recovery kit and separately held emergency recovery secret**; exact recovery medium, **recovery-kit wrapping/KDF**, rotation method and incident response still need implementation/security review; **ADR 0047** independently selects the SQLite record cipher.
8. Keep the existing [ADR 0037](0037-central-secret-broker-task-scoped-access.md) authorizations, [ADR 0038](0038-multi-account-isolated-cli-and-api-access.md) account isolation, [ADR 0044](0044-encrypted-sqlite-secret-storage.md) SQLite storage policy and hard project budget approval. The initial worker cloud remains AWS ECS Fargate under [ADR 0041](0041-aws-fargate-first-real-worker.md), but worker tasks must **never** receive the controller master key.

## Alternatives

- **Manual unlock on every startup:** explicitly not selected, because it blocks autonomous restart.
- **Mandatory hosted KMS/Secrets Manager/Vault:** not selected for this first version; may be proposed later but cannot silently replace the approved local key file.
- **Key stored in SQLite, Git, image, source, regular database backup or browser:** prohibited.
- **Regenerate a new key whenever a file is missing:** prohibited; creates unrecoverable encrypted records and potentially unsafe account behavior.

## Test requirements (not executed)

- Ordinary restart reads the existing protected key and decrypts only authorized test credentials without human intervention.
- Incorrect/missing key, broad file permissions, wrong owner, key/record mismatch and deliberate symlink attack block access **without overwriting the database or generating replacement keys**.
- SQLite DB/WAL/ordinary DB backup, repository and worker images do not contain the key or plaintext secret material.
- User/project/attempt and fenced-lease checks still deny unauthorized secret access after automatic startup.
- Recovery of an older encrypted DB snapshot with a separately safeguarded matching recovery key succeeds **only through an explicitly controlled restore workflow**; rotation preserves versioned recoverability.
- Tests record host/process threat limitations and demonstrate that no fake claims of root-compromise protection, production security review or actual implementation have been made.

## Still open (OQ-005/P0)

[ADR 0047](0047-secret-broker-xchacha20-key-hierarchy.md) approves the record AEAD, KEK/DEK and guarded first-time-only setup. Exact cryptographic crate versions/record format, protected file provisioning and runtime path, atomic crash-safe first-time creation details, key versioning and rotation, the ADR 0046 approved off-host kit's actual storage medium and restore security, host hardening/identity, worker bootstrap attestation and secret-access incident handling. **The choice between automatic vs manual startup and the initial local-file custody model is closed.** Other P0 questions, especially real provider subscription rights OQ-008, remain open.
