# ADR 0043 — Single application bundle, browser platform completeness and UX/design boundary

Status: **Approved architectural and delivery constraints; exact UI design deferred**
Date: 2026-10-25
Owner decision: explicitly accepts the proposed React/TypeScript, Vite, React Flow, Rust/Axum REST + SSE frontend direction and requests a single minified application JavaScript bundle containing compiled CSS, no embedded fonts/icons, comprehensive relevant browser support, and UX-first decisions without selecting UI aesthetics.

## Decision

1. **Approved frontend stack:** React + TypeScript, built with Vite. React Flow is the planned **read-only activated-DAG visualization**; the accessible hierarchical task tree is distinct. Only the already-approved Rust Axum backend and SQLite/SQLx authorize and persist data. Use authenticated JSON REST for snapshots and commands and authenticated SSE for read-only live status notifications; a fallback/reconnection contract is mandatory.
2. **Exactly one emitted application JavaScript asset** in the production distribution, minified and content-hashed (illustratively `app.[hash].js`). All production application modules, React dependencies, graph code and bundled CSS are incorporated into that **single application JS**. **No separately emitted application CSS, dynamic JS chunks, library/vendor chunks or standalone JS polyfill bundle.** This is a **production build constraint**, not a requirement to write all source code in one file.
3. **Mandatory separate browser assets are allowed and required.** `index.html`, `manifest.webmanifest`, external application icons and **`sw.js`** are not embedded inside the application JS. A Service Worker must be loaded from its **separate JavaScript URL** and is the deliberate exception to 'one JS' when counting all .js files in the distribution. Its code must not be split into supplementary worker chunks. Other workers/worklets, if ever needed, require a separately approved exception or a design compatible with this constraint.
4. **Never bundle or inline font and icon payloads.** No WOFF/WOFF2/TTF/OTF, icon fonts, base64/data URLs, embedded icon SVG markup, packaged icon glyph/component libraries or icon images included in JS/CSS/HTML. Fonts and icons are fetched as **separate URLs/assets**, selected and reviewed in the later UI design stage. Google Fonts is an eligible **candidate** but not selected or required; use accessible system-font fallbacks when offline, blocked or missing. The icon **provider, icon set, font families, sizes and actual visual assets are all deferred**. Functional icon alternatives must retain text labels even when icon requests fail. Existing approved Rolvya visual identity must not be replaced.
5. **Browser/PWA readiness:** provide the applicable standards-based files, metadata, manifest, icons, service worker, accessibility/i18n affordances, security policies, offline and install behavior, and verified capability fallbacks as detailed in [browser platform contract](../architecture/web-platform-artifact-and-capability-contract.md). Support commonly deployed modern browsers through a documented and tested compatibility matrix, **not** an impossible promise that every browser implements every Web API.
6. **UX before visual UI:** approve UX principles and verifiable user journeys (not visual designs), including accessibility, keyboard operation, understandable errors, action previews, authorization clarity, offline/sync clarity, DAG/tree separation, status provenance and recoverable navigation, as detailed in [UX contract](../product/web-ux-and-accessibility-contract.md). No fonts, icon provider, component look, spacing, exact colors, layout aesthetics or graphics are selected by this ADR.
7. **Browser features are gated by purpose and capability.** Prefer progressive enhancement; only request notifications, clipboard, file access, sharing or other permissions in relevant user-triggered flows. Do not enable Web APIs merely because a browser supports them. Privacy and security take priority over feature count.
8. **Security/financial authority stays server-side.** The Service Worker never authorizes or queues paid actions offline, caches protected API/credentials/audit/billing data, or bypasses fresh Owner confirmation. Sensitive actions fail closed when offline or unauthenticated. Hard budget, fixed DAG, remote-only Git, provider-entitlement and task-scoped secret rules remain unchanged.

## Why and tradeoffs

The Owner prioritizes a simple, predictable frontend artifact with one cacheable application JS and no locally bundled fonts/icons, even though disabling code splitting typically increases initial JS download/parse size and may reduce route-level caching. Build-time TypeScript module boundaries are unaffected. CSS-in-JS at build output needs a carefully tested CSP-compliant runtime style insertion strategy; Vite's `cssCodeSplit: false` **alone still emits a CSS file**, so an explicit CSS-to-JS pipeline and output validation are required. Content-hash/cache/rollback strategy must account for all-or-nothing bundle changes.

A plugin that inlines both code and styles directly into `index.html` is **not** acceptable as the default solution: the Owner asked for **one external JS file**, not a single self-contained HTML. Select/build a verified pipeline at implementation time without committing to an unreviewed plugin.

## Mandatory validation gates before any 'complete' claim

- Verify recursively that exactly **one application JS asset** and **one standalone `sw.js`** exist, with **zero production .css or additional executable .js chunks**; non-application supporting files allowed only per approved catalog. No injected inline scripts, fonts, icon glyphs or base64/data-URI assets.
- Verify application CSS is minified within application JS and actually applies under a **strict CSP** without requiring blanket `unsafe-inline`, `unsafe-eval` or disabling security protections; external font/icon hosts, once chosen, must use allowlisted origins and explicit fallback. Browser CSS/JS browser-target compatibility checked at actual locked Vite version.
- Verify install/upgrade/offline/online/Service Worker lifecycle with no private response cache or stale approval replay; manifest and icons validate where supported.
- Automated accessibility plus keyboard/screen-reader manual tests against WCAG 2.2 AA, RTL/pseudolocale and translated copy overflow, and at least one meaningful cross-browser matrix including mobile browsers.
- Test HTTP headers, i18n, resilient SSE, reduced motion, permissions denied, unsupported API fallback, no-JS/auth failures, and user-facing cost/approval clarity.
- Publish actual build file inventory, verified test logs and known browser limitations; do not claim implemented capabilities based only on this decision.

## Explicit non-decisions

No approved UI visual design, font family, icon library/provider, exact icon assets, theme palette token assignments, component kit, animation, frontend routes, one-off web feature requiring invasive permissions, concrete locale list, browser-version floor, PWA offline data scope, deployment ingress, asset origin/hosting, SW strategy, or security header values. These are implementation/UX acceptance details to review without silently changing security policy. The five approved top-level sections from [ADR 0042](0042-five-section-web-panel-navigation.md) are unchanged.

This ADR is **not** executable frontend code, a built distribution, an audit of every browser version, or authorization to launch cloud resources.
