# Rolvya v0.1 — implementation defaults and release gates

## Decision authority and scope

On 2026-10-25 the Owner requested that the assistant **resolve all remaining routine topics step by step without repeated micro-approvals or documentation churn**. This document chooses **initial engineering defaults** for the 13 OQ items; it is **not** a retroactive claim that individual selections are separately Owner-approved ADRs or that code/tests/provider permissions exist. Binding earlier approved ADRs, security and hard-budget gates prevail over all details below.

**Rule:** implement with the defaults; change a default only for measured correctness/security/compatibility reasons and record a concise reason in the relevant PR. **Never** silently approve new spend, credentials, external provider access, sensitive Owner actions or alteration of an already activated DAG. A decision is not verified execution evidence.

## Important cross-cutting implementation gate not separately numbered in OQ list

**GitHub App integration:** Default to repository-selective App installation. Request minimum **Contents** access for clone and isolated branch writes; additional Pull Requests/Checks permissions only for flows actually used, and **no Administration/workflow-write by default**. Use short-lived repository-scoped installation tokens only inside trusted Rust Git publisher, not worker prompts; webhooks require `X-Hub-Signature-256` verification and idempotent delivery handling. Never merge/protect branch bypass on behalf of an agent without authorized policy. Endpoint permission matrix is verified against actual APIs at implementation.

## Work sequencing and exit states

**Stage 1 — No-cost deterministic Rust core:** write tests for DAG freeze, SQLite concurrency/budget, retry, permissions, fake worker and model mode gates. Prior approval of architecture permits **synthetic code/tests** without cloud spending.

**Stage 2 — P0 security integration:** first-run key creation/restore, session and step-up controls, worker bootstrap, entitlement registry; use synthetic identities before live credentials. Supported API mode can be enabled only after authorized connection and actual use limits are proven.

**Stage 3 — Real AWS/Git integration:** deploy **only with a separate explicit spend authorization**, permitted provider accounts, GitHub App installation access and enforceable cap; measure provider cancellation/charges. No live costs are approved here.

**Stage 4 — Browser and release:** approved five-section UX, separately approved UI visual decisions, full PWA/i18n/accessibility/security validation, end-to-end receipts, release CI. Do not create frontend files until the Owner's earlier deferral is lifted.

**Stage 5 — Deferred P2:** additional Git providers and final artwork/trademark rules after a credible core release. These are not blockers for the fake core and are intentionally **deferred, not completed features**.

## Evidence required to claim a topic “completed”

All 13 have an initial **engineering direction** in this file, but **implementation and test gates remain incomplete**. An item may be called `Implemented` only when code exists; `Verified` only after repeatable tests. **OQ-008 legally permitted unattended subscriptions**, actual cloud IAM/cost and recovery test outcomes cannot be decided by implementation preference alone. Approved hard budget and human step-up rules remain binding.
